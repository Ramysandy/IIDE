# Engineering Decisions (spec section 22)

Choices below are implementation decisions, not construct changes. Items marked **CONFIRM** affect
replay validity or eligibility and should be reviewed and pre-registered before the main experiment.

| ID | Decision | Rationale / consequence |
|---|---|---|
| D-01 | Python 3.11+ only (developed on 3.13.5). | Spec 0.11. |
| D-02 | FastAPI for the toy service, driven in-process by `fastapi.testclient.TestClient`; `httpx` is a dependency of the test client. | Spec allows FastAPI or Flask. No `uvicorn`: no socket is ever opened. Starlette currently emits a deprecation warning that `httpx` should be replaced by `httpx2`; not acted on in Phase 1. |
| D-03 | **Isolation = fresh Python subprocess per replay** (`python -I -B`), scrubbed environment (`PATH`, `HOME`, `TMPDIR` only), private temp dir, oracle-owned event sink. No Docker; outbound network is **not** blocked. | Docker CLI exists on this machine but was not used or verified. Stronger isolation (container, network off, workspace without oracle artifacts per spec 11.2) is Phase 4 work. **CONFIRM** before agent runs. |
| D-03a | Harness contract: the worker calls `app.main.create_app(sink=...)` and the app emits through `app.telemetry.Telemetry.emit`. The sink is supplied by the worker, not by the code under test. | The oracle controls where events are collected. Consequence: an agent that moves telemetry out of `Telemetry`/`sink` (e.g. a logging-library migration) would not be observed. **CONFIRM** how F5 is handled in Phase 2. |
| D-04 | Detection decision exactly as spec 6.2/7.1: decidable iff `v >= ceil(0.8*k)` (computed as `ceil(80*k/100)` with an integer numerator), then `d=1` iff `fired >= ceil(v/2)` (a tie counts as detected); otherwise `UNKNOWN`. Majority is over valid `v`, not planned `k`. | Spec's recommended pre-registration. `attack_detected` lives in `iide/replay/reliability.py` because the baseline needs it now; Phase 3 `scoring/coverage.py` may re-export it. |
| D-05 | **Flake rate** = `(invalid replays + valid replays in the minority outcome) / k`. Pilot limit is `< 5%` (strict), from proposal gate G3. Also reported separately: invalid-replay rate and outcome-disagreement rate. | The spec/proposal require a flake budget but give no formula (searched `docs/`). With k=5 the measurable values are 0, 0.2, 0.4, ..., so a 30-replay calibration is also run. **CONFIRM.** |
| D-06 | Attack-level alert policy `any_expected_rule`. Redundancy `r(a,P)` is the union of event types of *fired expected* rules only; raw count, distinct-type count, firing-rule count and redundancy count are separate fields (spec 8.2). | Only one rule exists in Phase 1, so the policy is not yet exercised. |
| D-07 | Invalid replays are `TIMEOUT` or `INFRA_ERROR` (worker crash, nonzero exit, missing emulation, vanished sink) and are never counted as silent. Events that fail schema validation after normalization are excluded from detection input and counted in `schema_invalid_event_count`; malformed JSONL lines are counted in `malformed_line_count`. Baseline fails its exit criterion if either count is nonzero. | The treatment of schema-invalid candidate telemetry (vs `FORMAT_DRIFT`) is a Phase 2/3 question. **CONFIRM.** |
| D-08 | Normalizer is minimal: aware timestamps -> UTC with `Z`; severity stripped and upper-cased. `event_type` is never rewritten; naive timestamps are not assumed to be UTC. | Spec 4.1, 6.3. Anything more is a pre-registration decision. |
| D-09 | Event schema requires all 12 spec fields as non-empty strings (`attributes` an object), forbids extra top-level fields, and rejects secret-like attribute names (`password`, `passphrase`, `secret`, `token`, `api_key`, `credential`). | Spec 4.1 "no secrets". Allowing null `actor_id`/`target_id` would be a schema-version change. |
| D-10 | Catalog `security_bearing` labels are **provisional**: `auth.login_failed` and `auth.lockout` true; `auth.login_success` false. | `S_sec` must be pre-registered in Phase 2. **CONFIRM.** |
| D-11 | Frozen hash groups: `rule_pack_hash`, `attack_set_hash`, `telemetry_contract_hash`, `detector_engine_hash`, `replay_harness_hash`, `testbed_source_hash`. A test fails if the committed baseline's hashes differ from the current files. | Freeze policy, spec 6.1. Any edit to `iide/replay/*`, `iide/detection/*`, the normalizer, schema, catalog, rules or attacks invalidates the Phase 1 baseline and needs a new baseline and `experiment_version`. |
| D-12 | `git_commit` is `null` with an explanatory note because the folder is not a git repository. Content hashes stand in for commits. | Spec 4.5 expects commits; initialising git was not requested. |
| D-13 | Layout deviations from spec section 2: omitted for now `configs/experiment.yaml`, `configs/agents.yaml`, `schemas/run_record.schema.json`, `schemas/instruction.schema.json`, `testbeds/shared/`, `testbeds/<tb>/telemetry_schema.json`, `testbeds/<tb>/detection/runner.py`, `iide/scoring/*`, `iide/runner/*`, `iide/analysis/*`, `iide/cli.py`, `scripts/{run_pilot,score_runs,verify_reproducibility}.py`. Added `scripts/validate_testbed.py`. | Spec says not to create empty placeholders. Per-event field requirements live in `event_catalog.yaml`; loading and cross-validation live in `iide/replay/runner.py`. |
| D-14 | Testbed tests are split: **functional tests** (agent-visible, use a discarding sink, do not import `iide`) are in `testbeds/billing_api/tests/`; **telemetry, detection and replay tests** are in `tests/`. | Spec 5.1/11.2: functional tests must not depend on telemetry, and oracle code must stay out of the agent workspace. |
| D-15 | ATT&CK `T1110` is a research label with `technique_mapping_status: UNVERIFIED` and no framework version. | Spec 4.3 requires validating the mapping and recording the ATT&CK version; not yet done. |
| D-16 | Lockout counters are tracked for every `account_id` (known or not) and lockout is permanent per instance. | Avoids account enumeration; every replay uses a fresh instance. |
| D-17 | Replay IDs are `sha256(testbed_id|attack_id|program_ref|experiment_version|replay_index)[:16]`; correlation IDs are `replay-<attack_id>-<NNN>` (1-based). | Same construction as the spec 12 run-ID recommendation. Run IDs themselves arrive in Phase 4. |
